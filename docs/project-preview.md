# 预览项目修改

`ProjectStore.preview`、桌面 Python 的 `stk.project.preview` 和桥方法 `project.preview` 使用同一编辑引擎，
在 SQLite 内存副本上计算一批修改后的表格、引用和公式。它为批量修改和后续 AI 草案提供可检查的结果；
当前还没有 AI 对话页面；格式 6 已支持保存已检查草案及原子应用回执，见[草案指南](project-drafts.md)。

## 原生修改检查

“项目表格”编辑器新增 **表格 / 修改检查** 页签，可在应用前检查确定性草案：

1. 在单元格编辑器输入新的值、引用或公式，点击 **检查此单元格修改**。这会切换到检查页并计算预览，
   原项目仍保持不变。也可直接在检查页粘贴普通编辑命令的 JSON 数组，或点击 **填入示例**，再 **计算预览**。
2. 检查基础/候选修订、差异数量和公式错误数量。差异包含表格、字段、记录、单元格，以及受影响的派生值；
   新增/删除使用稳定 ID 对比，级联删除包含子对象和已有单元格，不把未设置值混为显式 `null`。
3. 在共享表格中选择一项，查看完整 UUID、修改前后的值、引用/公式定义及求值错误；
   **公式错误** 页包含候选项目全部错误，包括与本次修改无关的原有错误。
   仅 `evaluated_revision` 变化不计为差异。**实际应用的命令** 可展开检查预览生成的稳定 ID。
4. 明确点击 **应用已检查的修改** 才调用普通原子编辑；整个批次可通过项目“撤销”恢复。
   公式错误遵循普通编辑规则，允许保存错误状态，应用前不会自动修复公式。

差异表示整批命令执行后的最终表格状态，不是逐条命令日志；同值写入等没有净变化的批次仍可应用，
并按普通编辑规则递增修订、进入修改历史。需要检查具体动作时展开实际应用的命令。

修改 JSON 输入或清除草案会立即废弃旧候选；正在返回的旧预览也会丢弃。
项目修订变化后应用按钮失效，必须重新计算并检查，不会自动改变基础修订。
外部 CLI 写入即使尚未被界面观察到，最终应用仍由数据库检查原修订，冲突时刷新而不重放。
每次应用尝试消费当前候选，失败或结果不确定时也必须重新预览。

当前编辑区和候选仅在桌面项目会话中共享，关闭/切换项目或桥重启清除，不写入布局文件；
输入最多 **256 KiB、1–1000 条命令**。展开 **已保存草案**，为当前有效预览命名后点击
**保存已检查草案**，才会在格式 6 项目中保存稳定命令和基础修订。保存不应用参数修改。
重开后需主动载入并重新计算预览；原始修订已过期时，只能明确另起新草案后检查当前项目。
清除编辑区不删除保存记录；已应用回执在撤销表格后仍保留，不能再次执行原草案。
完整保存、丢弃和响应丢失后的恢复规则见[草案指南](project-drafts.md)。本页尚未接入模型。

## 从 Python 打开原生检查页

在原生界面中打开项目，然后在 Python 控制台运行：

```python
p = stk.project
base = p.snapshot()
accepted = p.review(
    [{"op": "create_table", "name": "拟议参数表"}],
    expected_revision=base["project"]["revision"],
)
print(accepted)  # {"accepted": True, "project_id": "…", "base_revision": …}
```

`review` 通过既有本地主线程请求通道激活第一个主窗口的项目编辑器，并显示“修改检查”；
没有项目页签时添加一个，不替换其他编辑器。原生端重新调用项目预览引擎，差异、稳定命令和错误
与手动预览相同。脚本只提供普通编辑命令，不能提供自报的前后快照或可应用候选。
**返回值表示请求已接受**，计算结果或命令错误随后显示在检查页。明确点击“应用已检查的修改”才写入数据库。

- 请求绑定 `p` 的桥会话句柄和显式基础修订。排队后切换/关闭项目或已观察到修订变化会返回 `conflict`；
  数据库还会在计算和最终应用时校验修订，未观察到的外部修改也不能被覆盖。不会自动重开或切换到 `p`。
- 已有草案、候选或预览错误时返回 `conflict`，保留原内容。先在界面检查并“清除草案”，再明确发起新请求；
  当前没有脚本覆盖/清除草案或自动点击应用的入口，重复请求也不会替换旧候选。
- 项目正在加载/操作，或任一桌面窗口仍在文本编辑状态时返回 `busy`。先结束当前输入；控制台运行按钮或
  Ctrl/Cmd+Enter 会先提交控制台源码。此规则也保护尚未失焦、尚未写回绑定的原生文本。
- 未连接桌面返回 `unavailable`，旧桌面未协商 `project.review` 能力时返回 `unsupported`；
  过期/分离会话请求不执行。超时或中断不回滚已经接受的预览，应先查看界面，不能盲目重试。

`review` 不等待用户审批，不准备运行、不提交任务，也不自动持久保存草案；可在原生检查页另行保存，
或通过 `p.drafts.save(...)` 明确保存，二者不等同于应用。
只想让脚本拿到完整候选数据时，继续使用下面的 `preview`；它不会打开检查页。

## 先预览，再明确提交

```python
p = stk.project
base = p.snapshot()
proposal = p.preview(
    [{"op": "create_table", "name": "拟议参数表"}],
    expected_revision=base["project"]["revision"],
)
print(proposal["persisted"])          # False
print(proposal["snapshot"]["tables"]) # 假设提交后的表格
print(p.snapshot() == base)           # True：实际项目没有改变
```

返回值包括：

| 字段 | 含义 |
|---|---|
| `persisted` | 始终为 `false` |
| `base_revision` | 被读取的项目修订，也是后续提交的前置修订 |
| `proposed_revision` | 假设提交成功后的修订，等于基础修订加一 |
| `commands` | 校验后的命令，含自动分配的稳定 UUID |
| `snapshot` | 假设提交后的项目快照；其中修订、公式缓存和撤销状态也是假设结果 |

检查内容后，可以在**另一次明确操作**中提交返回的命令：

```python
committed = p.apply(proposal["commands"], expected_revision=proposal["base_revision"])
```

不要重新提交原来缺少 UUID 的命令列表，否则会分配另一组 ID。每次预览都是独立计算，
未提供的 UUID 可能不同；预览不会在后台保留或自动应用草案。

另一个窗口或脚本修改项目后，旧预览仍是旧修订上的结果；提交会得到 `conflict`。
应读取新状态、重新生成并检查预览，不能只把 `expected_revision` 改成最新值后继续提交。
实际提交复用普通原子编辑和撤销机制，不新增数据库格式。

## 错误和副作用边界

命令、类型、对象或修订错误直接拒绝，与 `apply` 一致。公式中的循环、缺失来源、单位不一致等
仍按现有规则显示在候选快照的 `records[].evaluations` 中；预览成功不表示每个公式都有有效结果。
可以在提交前检查这些错误并修改草案。原项目的值和错误状态不会被候选结果覆盖。

预览只接受普通表格编辑命令，不接受文件复制、输入快照捕获、升级、运行方案准备或任务提交。
实际项目修订、修改历史、撤销/重做、文件内容和 Runtime 任务均保持不变；桥不发布 `project.changed`。
文件索引属于普通表格，候选索引信息也只存在于返回的快照中，不代表磁盘文件已经变化。

源库以只读事务建立一致快照，复制完成后释放读事务，再在内存里计算。
这允许外部 CLI/其他连接在候选求值期间写入源库；同一桌面桥的项目操作仍遵守既有串行会话锁，
不能据此承诺同一桥内的编辑与预览并行。
源库逻辑大小限制为 **128 MiB**，每批 **1–1000 条命令**；限制针对数据库副本大小，
不代表计算时的总内存上限。原生差异视图当前对完整候选做对比；大项目的增量预览留待后续扩展。
旧格式保持原格式：例如格式 1 可以预览字面量修改，但仍不能预览引用/公式，不会自动升级。

## CLI

```bash
suan project preview /absolute/project --commands edits.json --expected-revision 3
```

也可用 `--commands -` 从标准输入读取。输出是上述完整预览对象；需要保存并提交时，
把其中 `commands` 数组写入独立 JSON 文件，再明确调用 `suan project apply` 并使用 `base_revision`。
整个预览对象不能直接当作命令数组传给 `apply`。

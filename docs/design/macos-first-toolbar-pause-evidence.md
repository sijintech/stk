## 实际失败阶段

173 中必测 MP4 和 HTML 视频都失败在第 1 轮 `explicit-pause`，即首次可见工具栏暂停。此时还没有做 seek，也没有隐藏视图。只有 `lower_time_gt_0_05` 一项为假：MP4 从 0.10535 降到 0.03728 s，HTML 从 0.10089 降到 0.03291 s。两者都已收到 `pause_ack`，首个暂停样本时 `verified` 为假。断言失败后，250 ms 保持没有执行。

173 共有 6 个失败用例落在同一断言上：必测 MP4 和 HTML、`pre-seek-hide` HTML、`second-visible` MP4、`fresh-native-visible-dom` MP4、`visible-frame-clock` MP4。

## 四个首次工具栏样本臂（仅 173）

| 对照臂 | play() 返回时的 DOM | 请求距 play() 返回 | 早期 DOM（距派发） | 约 200 ms | 约 600 ms |
| --- | --- | --- | --- | --- | --- |
| MP4 立即 | 0.10634 | 0.04 ms | 0.10634（8 ms） | 0.03493 | 0.03493 |
| HTML 立即 | 0.12492 | 0.03 ms | 0.05946（26 ms） | 0.05946 | 0.05946 |
| MP4 延迟 | 0.12519 | 276.7 ms | 0.24131（18 ms） | 0.24131 | 0.24131 |
| HTML 延迟 | 0.11144 | 276.2 ms | 0.26844（31 ms） | 0.26844 | 0.26844 |

- 四条原生轨迹的顺序一致：`dispatch` → 焦点释放 → `hide`（2–21 ms）→ `suspend-ack` → `ack` → `show`（6–25 ms）→ `pause-under-suspension`（原始状态 3，56–96 ms）→ `reply` 3 → `release-ack` → `release-state` 2（117–172 ms）。也就是说，可见工具栏暂停同样走了 `bd4f3c32` 的挂起内暂停。
- MP4 立即臂 8 ms 时的早期样本与 play() 返回值逐位相同，200 ms 时已降到 0.03493。HTML 立即臂在 26 ms 时已经是降低后的值。
- 延迟臂在等待期间不读 DOM，所以只能说明三个暂停样本一致，不能据此认为 270 ms 等待消除了回退。按 play() 返回值外推，暂停时约为 0.125 + 0.277 ≈ 0.40 s，实测只有 0.241 和 0.268 s，差约 0.13–0.16 s。如果 play() 返回时实际位置接近 0，再加 0.277 s 正好约为 0.24–0.27 s。

| 169（7 个） | 1 个：0.0663 | 6 个 | 7/7 落在 0.041–0.066 |

- 两轮中几乎每次首次暂停都会在约 0.25 s 内落到 0.03–0.066 s。不含 `bd4f3c32` 的 169 也是如此，这是认为该提交引入此现象的反例。两轮中"首样本已降低"的比例不同（1/7 和 9/25），样本太少，不作归因。
- 0.05 下限是否通过，取决于两件事：首个暂停 DOM 回复（play() 返回后 0.019–0.061 s）是否晚于这次时钟变化；以及变化后的值落在 0.05 哪一侧。
- 回退后的值都在 10 fps 原片的第 0 帧 [0, 0.1) 内，但都不等于 0.0。原片的关键帧在第 0 和第 30 帧，因此"简单跳回关键帧"不成立。
- 反例：173 隔离静默 MP4 保持期间是 0.1306 → 0.1306，没有降低。

## 两个竞争假设

- **H1：DOM 时钟领先，随后校正（只有 DOM 变化）。** play() 在 DOM 首次 ≥ 起点 + 0.10 时返回，此时实际位置和画面仍在第 0 帧。暂停后，首个回复可能沿用领先的值，随后被校正为实际位置（0.03–0.066），画面从未显示第 1 帧。预期：从 play() 返回到暂停生效之间画面为 ID 0，暂停后稳定画面也为 ID 0。支持证据：读数 2；MP4 立即臂 8 ms 样本与 play() 值逐位相同；回退后的值全部落在第 0 帧内；延迟臂的算术也相符。
- **H2：实际回退。** play() 返回时播放确实在 0.10–0.13 s 并继续前进，画面显示过第 1 帧。随后暂停路径（轨迹中的隐藏、挂起、显示、挂起内暂停、释放）或 WebKit 的暂停让媒体位置退回 0.03–0.066，并重绘第 0 帧。预期：从 play() 返回到暂停生效之间画面 ID ≥ 1，暂停后稳定画面为 ID 0。不利证据：退回点不是关键帧；169 没有挂起内暂停也有同样的降低；延迟臂也必须同样退回约 0.13–0.16 s。

## 下一项判别观测（只提要求，由 Root 设计）

现在唯一缺的是：从 play() 返回到首次暂停生效（立即臂的 `release-state` 在 117–172 ms）之间，画面显示的是哪个 ID（下称 P）。暂停后稳定画面的 ID 记为 S。play() 返回之前的画面不能用来判别：那时连 DOM 也还在第 0 帧，两个假设都预期 ID 0。

1. 只用非门禁的帧标记槽位和标记片。必测 6 项及其 20 轮不变。
2. 必测时序不变：play() 条件（≥ 起点 + 0.10、`ready_state` ≥ 2）、play() 返回后直接点击工具栏、`paused()` 的首个 DOM 样本及其 0.05 / 2.6 / 未结束检查、0.25 s 保持与 0.10 容差、1 s 原生核验期限。不增加 DOM 探测。play() 返回到暂停派发之间不能放阻塞式截图：现有帧时钟的播放臂截了 5 张、每张 55–70 ms，把暂停推迟到 +0.306 s，本质上是延迟臂，看不到立即暂停时的降低。
3. **P（首选，匹配对照）：** 用同一标记片、同样的 play() 条件，不点暂停，从 play() 返回起按现有播放臂限制（2 s、最多 8 张、ID ≤ 24）连续截图。记录第一张完成截图的 ID、截图请求和完成时间，以及首次出现 ID 1 的时间（均相对 play() 返回）。H2 预期第一张就是 ID ≥ 1；H1 预期先是 ID 0，ID 1 晚些才出现。这条路径完全不碰必测流程；代价是 P 与 S 来自不同会话。读数 2 是 seek 之后的同类先例。
4. **P（同一会话的备选，由 Root 权衡）：** 在 play() 返回时发出非阻塞截图请求（`capture_window_evidence` 本身是挂起后轮询的），立即点击，事后再轮询结果。请求开销必须落在现有 20 ms 请求容差内。画面时刻与 2–21 ms 的 `hide` 重叠，所以标记读不出时一律记为不确定。截图本身也可能扰动合成。
5. **S：** 必测的首个暂停判定和保持完成之后，或下限失败刚记录、尚未抛出之前，在现有 3 s 暂停预算、最多 8 张的限制内，连续两次读到相同 ID。当前 MP4 标记片正是因为先抛出失败，才没有任何画面。
6. 同时记录 play() 值、首个暂停样本和保持结束值各自对应的帧 `floor(t·10)`。MP4 和 HTML 各跑一次。由于降低不一定跌破下限，无论下限是否通过都要分类。

判定表（P 来自第 3 条时，结论附带"跨会话"标注）：

| P（play() 返回到暂停生效之间） | S | 结论 |
| --- | --- | --- |
| ≥ 1 | 0 | 同一会话可证实画面实际回退（H2）。跨会话结果仅支持该假设 |
| 0（对照中 ID 1 晚于约 0.17 s 才出现） | 0 | 支持 DOM 领先后校正（H1）。离散采样仍可能漏掉短暂呈现 |
| ≥ 1 | ≥ 1，且 DOM 保持值在第 0 帧 | DOM 降到画面之下，是两个假设共同的反例 |
| 缺失 / 歧义 / 超时 / 失去绑定 | — | 不确定，不另作解释 |

## 限制

- 标记以 100 ms 为一档，能区分第 0 帧和第 1 帧，无法分辨 0.05 下限两侧。每张截图的画面时刻落在其 55–70 ms 延迟窗口内某处，P 只能给出这一精度的时刻。
- S 目前只有 1 例 HTML，且在保持和布局适配之后拍摄。标记片与原片字节不同，但几何、10 fps、第 0 / 30 帧关键帧和编码一致。
- ScreenCaptureKit 截图本身可能影响合成时序。原始状态 2 / 3 按 WebKit 公开枚举顺序读作 Paused / Suspended。各计数样本都很小。

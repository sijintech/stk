# Python 自动化、布局编程与机器间通信

更新：2026-09-28。状态：原生 Python 控制台、项目/Runtime API 与布局执行器已交付首版；完整操作覆盖与远程连接继续推进。
目标是在 STK 界面内用 Python 控制全部面向用户的操作、通过编程配置页面布局，
并让两台安装 STK 的机器既能直接通信，也能经 SSH 通信。
这些能力纳入[开发计划](../development-plan.md)，不表示当前版本已支持。

## 当前实现与缺口

| 能力 | 当前状态 | 依据 |
|---|---|---|
| 原生桌面调用本机 Python | 已有：C++ 启动桥子进程，通过 stdio NDJSON 请求/响应和事件通信 | [桌面桥 v1](../specs/stk-desktop-bridge-v1.md) |
| Python 项目操作 | 存储 API、CLI、项目桥接口、原生表格与 Python 面板共用项目命令 | [项目存储指南](../project.md) |
| 界面内 Python 控制台与完整操作 API | 原生多行输入、独立会话、项目/Runtime/Viewer/分析图 API、输出/中断与文件运行已实现；完整相机、导出等操作继续补齐 | [Python 指南](../scripting.md)、桥 v1 §14 |
| 布局编程 | 已通过 Python facade → 显式反向请求 → UI 主线程实现布局读取、校验应用与编辑器查询 | `stk_app` 的 `scripting_ui.cc`、桥 v1 §14 |
| 连接另一台 Linux 计算机 | 已有：客户端经已有 SSH 隧道访问 Runtime，或经 hub 访问节点代理 | [Runtime 远程连接](../runtime.md#远程连接)、[控制服务指南](../hub.md) |
| STK 内管理 SSH 连接 | 已有首版：OpenSSH Host 配置、原生 Jobs/CLI 入口、状态/断开、按需重连与进程清理；真实 macOS/Windows 远程链路待验收 | [SSH 指南](../ssh.md) |
| 任意两台 STK 直接互通 | 尚无通用对等连接、配对与能力协商；当前 Runtime、hub 和节点代理服务端只支持 Linux | Mac/Windows 目前是客户端，不能把安装桌面等同于启动通信服务 |

“桌面桥”解决本机进程互通；“远程连接”解决不同机器互通。直接连接与 SSH 都可承载远程协议，
SSH 不是业务功能的另一套实现，也不等同于对等发现、项目同步或多人协作。

## Python 是完整的操作入口

所有面向用户的业务操作应具有可发现、可组合、可测试的 Python API：项目与表格读写、参数与节点图、
批次运行与取消、文件资源、结果查看/导出，以及工作区和布局。鼠标操作、Python、CLI 和 AI
调用同一套命令与校验规则，逐步消除“只有按钮能做”的功能。

建议建立操作目录，声明名称、参数/结果类型、所需上下文、执行位置、能力要求、进度/取消与撤销语义。
已有 `ProjectStore.apply`、Runtime 幂等提交和图求值 API 是可复用基础；不为脚本另写一套数据库或调度器。
API 通过对象身份或明确的上下文工作，避免依赖当前焦点、屏幕坐标和模拟鼠标点击。
首版 facade 为注入的 `suan.scripting.API`（`stk`），操作目录仅列出实际开放的能力；完整注册协议继续演进。

界面内提供 Python 控制台：多行输入、历史、补全/帮助、标准输出/错误、异常堆栈与中断/重启。
支持运行 `.py` 文件并保存可复用脚本；完整代码编辑继续使用 VSCode，不在 STK 内重建 IDE。
长期可提供操作记录到脚本的能力，记录稳定的语义命令而非鼠标事件。

优先验证独立 Python 会话进程：脚本死循环或本地原生扩展失败不应拖死 UI，也不占据桌面服务桥的协议流。
长操作异步返回任务/句柄，输出与协议消息分离；中断脚本与取消已提交的远程任务是不同操作。
这是用户代码执行环境，不因放进子进程就成为安全沙箱；项目脚本不在打开项目时自动执行。

## 布局也可以编程

Python 布局 API 覆盖区域拆分/合并、编辑器类型与标签页、尺寸比例、显示/隐藏、最大化、工作模式切换，
以及保存/恢复布局预设。项目/对象 ID 与 UI 会话中的区域 ID 分开，失效句柄报告明确错误。

复用现有 `Screen` 和 `LayoutFile`，由 C++ UI 主线程执行结构修改；后台 Python 不直接持有或修改
窗口/GPU 指针。新增请求方向必须明确相关 ID、超时、错误和会话寿命，不能把任意事件假装成桥 v1 已有的反向 RPC。
当前选择显式的可发现桥扩展（v1 §14）：会话 ID、请求 ID、到期时间与单独的回复方法，
原生主线程执行器在当前事件结束后处理；不引入第二套任意事件解释规则。

建议同时支持操作式 API 与可序列化布局描述。应用整份布局前校验编辑器类型、比例和结构，
失败保持当前可用布局；保留恢复默认布局入口。布局描述与 Python 源代码分开保存，恢复布局无需执行脚本。
个人布局偏好留在用户配置；项目可携带可分享的布局预设，不强制覆盖另一台电脑的窗口几何和个人设置。

## 两台机器之间的统一连接

目标是让 Linux/macOS/Windows 上的 STK 都能按自身能力成为连接端点；每次连接显式确定目标机器、
项目和可选桌面会话。轻量通信服务与当前 Linux 计算调度服务分开，不以取消 Runtime 平台限制代替跨平台通信设计。

| 方式 | 目标行为 |
|---|---|
| 直接连接 | 两端可达时，显式启用端点并配对，无需中心 hub；支持身份认证、加密和能力协商 |
| SSH 连接 | 复用用户 SSH Host 配置与现有认证；STK 管理隧道生命周期、状态与重连，通过隧道访问相同业务接口 |
| Hub 连接 | 保留现有集中接入与执行节点管理路径；按能力适配共同的客户端接口 |

首版优先显式输入地址/SSH Host，不将自动发现、NAT 穿透或公网中继视为已经解决的问题。
SSH 优先采用隧道复用现有端点；是否支持 SSH stdio 启动远端服务，另做启动/版本/寿命验证。
SSH 登录成功不自动获得所有项目权限，也不意味着远端服务已经安装、启动或具有全部能力。

两端先协商协议版本、文件访问、项目读写、图求值、任务运行和桌面控制等能力，缺失能力明确报告。
无界面的节点可以执行其支持的数据操作，但不提供窗口/布局操作。远程 UI 控制必须明确绑定并授权目标桌面会话；
普通文件或任务连接不隐含任意远程 Python 执行权限。连接凭据保存在用户配置，不写进共享项目或导出脚本。

大文件沿用分块、断点续传和校验的原则，与命令消息分离；路径属于目标机器，不把本地路径直接当远程路径。
写请求使用幂等身份，断线恢复要核对结果，不能盲目重复运行模拟。持续任务的寿命独立于桌面和隧道。

首版远程项目由一个明确的所有端服务写入，使用修订冲突检查；不让两台机器共享打开同一个网络盘 SQLite 文件。
传输项目副本不等于实时协作或自动合并，后两者仍是独立的后续能力。

## 建议实施顺序与验收

1. **P1 接口基础**：盘点操作覆盖；统一项目命令上下文；验证 Python → C++ 主线程的控制通道和布局往返。
   验收脚本能查询状态、修改项目、拆分区域并恢复布局；无效布局不破坏当前界面。
2. **P1/P2 控制台**：界面内执行 Python，接入输出/错误与中断；让 UI、脚本和 AI 共用命令。
   验收同一编辑产生相同修订/校验结果，脚本阻塞可恢复，服务桥与已提交任务保持可用。
3. **P2 SSH 管理**：先在已有 Linux Runtime 路径上自动建立/关闭/恢复隧道；验证错误 Host、端口冲突、
   认证失败、断线与幂等重试。用户已建立的外部隧道仍可使用。
4. **P2/P3 直接互通**：实现跨平台轻量端点、配对与能力协商，复用项目、文件和操作接口。
   两台真实机器验证双向发起、文件校验、修订冲突和断线恢复，覆盖 Mac↔Windows 及连接 Linux。
5. **持续补齐覆盖**：用“UI 操作—Python 操作”清单跟踪所有公开功能，纳入新增编辑器的验收；
   对需要桌面会话、计算平台或可选依赖的操作明确前置能力。

后续交付按[Python 指南](../scripting.md)维护状态；显式反向请求已作为桥 v1 的可发现增量扩展发布，
不改变原有请求方向和方法的语义。网络服务尚未实现。

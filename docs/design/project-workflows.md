## 目标

P3 验收要求：从项目流程进入分析子图并返回；图端口类型错误可定位；一份流程应用于多行运行；
参数变化后保留并标明旧结果，按范围重算。示例项目已经走过“参数扫描 → 合成求解 → 文件快照 → 分析”，
W3 让这条过程成为一份可见、可检查、可编辑的项目对象；按行执行与过期传播放在 W4，以已有执行服务完成。

## 决定一：新文档类型 `stk.workflow/1`，存为受管表格

**推荐**：工作流是独立的实验文档 `stk.workflow/1`，与保存分析相同的方式保存：一张固定 UUID
（`urn:stk:project:workflows:1`）的受管普通表格，每行一份工作流（名称、格式、文档 JSON），
沿用记录 UUID、预期修订、修改历史和撤销。只要求项目格式 ≥ 3，**不需要新的项目格式**。

**不采用**：在 `stk.graph/1` 中加入“子图节点”或发布 graph 新主版本。graph v1 是同一进程内按节点目录求值、
传递数据集与 payload 的数据流；工作流步骤引用项目对象（表格、快照、保存分析、仿真模板），经批次、Runtime
或分析运行执行，失败、取消、过期的语义都不同。[项目数据模型](project-model.md)已规定层级与项目身份不是 graph v1
的能力，破坏性变更须用新主版本；把两者混在一份文档中，`graph.validate`/`graph.evaluate` 会把项目步骤误当成可求值节点。

文档沿用 graph 的书写习惯（`id`、`inputs` 中的 `{"from": "步骤.端口"}`、`ui.positions` 不参与语义），
但顶层用 `steps`/`kind`/`ref` 而非 `nodes`/`type`/`params`，使工作流不会被误当作 graph 读取或求值。
W1–W2 的候选副本、改动清单、布局与拖线算法可以复用，但现有草稿按 graph 键名编写，W3c 需要先把这部分抽成可按文档种类
配置的共用代码；画布与视图模型（节点卡片、端口、连线）可直接复用。

## 决定二：步骤种类只引用已有对象

首版四种步骤，每种对应一个已有的项目对象和已有页面；工作流本身不复制这些对象的内容：

| 种类 | 引用（`ref`） | 输出端口（类型） | 输入端口（类型） | 进入/定位 |
|---|---|---|---|---|
| `table` 参数表 | 项目表格 UUID | `rows`（行集合） | — | 打开项目表格并选中该表 |
| `simulation` 仿真 | 已注册批次模板 `muferro/1` | `files`（每行收集的结果文件） | `rows`，须来自模板自己的案例表 | 打开“仿真批次” |
| `files` 输入文件 | 输入快照 UUID | `files` | — | 打开项目文件与快照 |
| `analysis` 分析 | 保存分析 UUID | 图 `outputs` 的每个名称（`result`） | 图中每个文件绑定名（`files`） | **进入子图**：分析图编辑器 |

报告步骤属于 P4；技能不直接成为步骤（见决定六）。未知种类、找不到的引用和不允许的端口类型都保留原文并在校验中报告，
不自动删除或替换。

## 决定三：子图边界取自保存分析本身

分析步骤的边界不另设格式，直接由被引用的保存分析声明：

- **输入**：带 `binding` 参数的源节点（目前为 `stk.source.file@1`、`stk.source.table@1`、`stk.source.muferro_run@1`）
  中的绑定名，例如体绘制预设的 `data`；每个绑定名是一个 `files` 输入端口，与分析运行“文件映射”中的绑定名相同。
  首版只认字面量绑定名，`binding` 写成 `$param` 引用时报告为不支持，而不是猜测取值。
- **可暴露参数**：图的 `parameters` 声明（名称、类型、默认值、标签），即节点中 `{"$param": …}` 引用的那些参数。
  工作流步骤可为其中任意一个给出字面量或参数表字段引用，未给出时使用保存分析的提交参数，再退回图默认值。
- **输出**：图的 `outputs` 名称，例如 `view`、`image`。

因此在 W1–W2 中改图（增删 `source.file`、改 `binding`、公开或撤回输出、增删图参数）就是改子图边界；
工作流校验会把失效的连线定位到具体步骤和端口，例如“`analyze.data`：分析中已没有该绑定”。

## 决定四：编辑时跟随当前修订，运行时冻结

**推荐**：工作流按 UUID 引用保存分析和其他对象（不按名称），编辑与校验时总是读取对象的当前修订，
画布显示被引用分析的名称、修订与内容哈希前缀。执行时（W4）冻结一份“工作流快照”：工作流规范 JSON 及其 SHA-256、
所选行 ID，以及每个步骤生成的已有运行记录——仿真运行记录冻结参数与输入，分析运行冻结完整图与文件映射。
“模板版本”就是工作流快照的哈希加上各被引用对象的内容哈希。之后修改工作流或保存分析，不改写已完成运行；
W4 用这组哈希与当前定义比较，标出过期的行和步骤，作为“影响范围”。

**不采用（可选）**：步骤钉住保存分析的某个修订，修改分析后须在工作流中明确“更新到最新”。它让升级成为显式动作，
但项目内同一分析需要保留多个历史修订内容，而受管表格只保存当前值；首版不建议。

## 决定五：两层导航与面包屑

- 新增“工作流 / Workflow”编辑器（区域编辑器下拉框与工作台入口），画布复用分析图画布，步骤卡片显示种类、引用对象名称与
  诊断。双击分析步骤或点击“进入分析”时，同一区域切到“分析图 → 保存的分析”，按 UUID 明确读取该分析。
- 分析图页头显示面包屑“工作流名 › 步骤名”和“返回工作流”。返回时恢复工作流的选中步骤与视图；未保存的分析草稿保留在
  分析图中，不因返回而丢弃。分析图已有其他分析的未保存草稿时，进入另一步骤沿用现有保护：拒绝替换并提示先保存或放弃。
- 面包屑绑定项目打开句柄；关闭或切换项目后清除，旧回调不能把视图带回旧项目。
- 首版只有两层：工作流 → 保存分析。工作流引用另一工作流（子流程）留作后续，格式预留 `workflow` 种类并要求引用无环。
  其他步骤只“定位”到已有页面，不进入子图。

## 决定六：技能经保存分析间接使用

技能目录中的项目固定版本与随项目保存的规则尚未实现（见[技能目录](../skills.md)）。首版工作流不直接引用 `id@version`，
需要使用某个技能时，先把其图预设保存为项目分析（查看器载入预设后在分析图“当前参数”中保存为新分析），
工作流再引用该保存分析。这样工作流引用的内容总在项目内，不会随全局目录更新而漂移。

## 连线的四种语义

沿用项目工作台设计中的四种关系，不用一种无类型连线替代：

| 关系 | 在工作流中的表示 | 首版行为 |
|---|---|---|
| 数据流 | `inputs`：`{"from": "步骤.端口"}`，端口类型 `rows`/`files`/`result` 须匹配 | 校验类型与存在性；W4 执行时传递 |
| 参数依赖 | 步骤 `parameters` 中的 `{"$field": 字段 UUID}`（仿照图的 `$param`，不与对象字面量混淆），字段须属于上游参数表 | 校验字段存在且类型兼容；W4 按行取值 |
| 执行依赖 | 步骤 `after`：必须先完成的步骤 ID 列表 | 画布虚线；校验存在且无环 |
| 对象关联 | 不存入工作流；运行、文件与步骤的归属由运行记录推导 | 导航与筛选 |

数据流与执行依赖合起来必须无环；不把求解器内部迭代解释为图循环。

## 文档草案

```json
{
  "format": "stk.workflow/1",
  "steps": [
    {"id": "cases", "kind": "table", "ref": {"table": "<表格 UUID>"}},
    {"id": "fields", "kind": "files", "ref": {"snapshot": "<快照 UUID>"}},
    {"id": "analyze", "kind": "analysis", "ref": {"analysis": "<保存分析 UUID>"},
     "inputs": {"data": {"from": "fields.files"}},
     "parameters": {"colormap": "cividis", "path": {"$field": "<文件名字段 UUID>"}}}
  ],
  "ui": {"positions": {"cases": [0, 0], "fields": [240, 0], "analyze": [480, 0]}}
}
```

名称存在受管表格的名称字段中，不重复写入文档。上限沿用保存分析的量级：每项目 128 份工作流、每份 200 个步骤、
文档 256 KiB；超限拒绝保存而不截断。

## 校验

`workflow.validate`（名称待定）只读取项目当前记录，不运行节点、不准备运行、不调用模型，报告带步骤 ID 与路径的问题：
重复或非法 ID、未知种类、引用不存在（包括被删除的分析或快照）、端口不存在或类型不符、仿真 `rows` 不来自模板案例表、
参数字段不属于上游参数表或类型不兼容、引用的图参数未声明、`after` 指向不存在的步骤、环。与分析草稿一致，
保存工作流不要求校验通过（文档是草稿），执行前（W4）必须通过。

## 与批次、运行和过期的关系（W4 预告）

详细方案见[工作流按行运行、过期与重算](workflow-runs.md)。

- “一份流程应用于多行”：参数表步骤给出行；对所选行运行工作流时，每行是一个实例，复用同一定义并按行取字段值，
  不复制节点图。仿真步骤以这些行保存一个[仿真批次](../simulation-batches.md)，分析步骤为每行准备一次分析运行。
- 工作流运行记录只保存工作流快照、所选行和各步骤生成的运行 ID；冻结的参数、输入与结果仍归原有运行记录所有。
  这需要一张只追加的新表，即**项目格式 10**，沿用“备份并升级项目”的显式迁移；W3 不需要。
- 分析运行目前使用保存分析的提交参数，按行绑定参数需要准备时接受并冻结参数覆盖值；这是 W4 对分析运行的扩展。
- 仿真结果须先登记并捕获为输入快照才能交给分析运行（现有规则），W4 把这一步做成工作流中的显式动作，不自动猜测文件。

## 所有者决定（2026-10-07 确认）

以下四项均按推荐执行：


1. **文档类型与存储**：采用新实验格式 `stk.workflow/1` 并存为受管表格（不升级项目格式），而不是扩展 graph 主版本？
2. **引用版本**：编辑时跟随被引用对象的当前修订、执行时冻结并以哈希显示影响范围，而不是钉住修订后显式升级？
3. **首版范围**：两层（工作流 → 保存分析），步骤只含参数表、`muferro/1` 仿真、输入快照、保存分析四种；
   子流程嵌套、技能直接引用与报告步骤推后？
4. **示例求解器**：是否把示例项目的合成求解器注册为本机模板（例如 `demo-synthetic/1`，不经 Runtime），
   使 W4 可以离线验收“参数表 → 仿真 → 分析”的完整按行运行？——确认注册，在 W4 实现；在此之前示例工作流从输入快照开始。

另需在 W3b 处理术语：仿真面板现有“正在执行工作流操作…”“Python / 工作流输出”中的“工作流”指模板脚本操作，
引入“工作流”编辑器后改为“仿真操作”，避免与项目工作流混淆。

# 草案、对话上下文与恢复边界

状态：2026-09-29。格式 6 的[持久草案与应用回执](../project-drafts.md)已实现；格式 7 增加
[显式上下文、文字消息及草案来源关联](../project-contexts.md)。首版不依赖模型服务。
完整 AI 主页面、模型生成请求与工具执行仍是后续开发范围。

原生项目编辑器已增加“讨论”页，提供显式选行/字段捕获、分页记录、消息填写及当前已保存草案的来源关联；
“修改检查”显示来源并提供明确刷新入口。文字以普通文本展示，不渲染 Markdown 或执行代码。
本机与跨平台验证状态分别记录在[开发计划](../development-plan.md)和[验收记录](../runtime-validation.md)，
此处不把实现等同于全部平台验收完成。

## 统一修改接口

普通项目命令共用 `apply` 与只读 `preview`。原生检查展示确定性差异和公式错误；
`stk.project.review` 可以把 Python 提出的命令送入该视图。持久草案保存稳定命令、项目 UUID、
基础修订及终态回执，不保存模型授权、差异快照或审批身份。

保存不更改参数；应用参数修改、准备运行方案和提交计算分别由明确操作触发。
重开项目不执行草案；已有回执不会因撤销参数而恢复为待执行状态。这些边界保持不变。

## 显式上下文捕获

格式 7 的首版仅捕获一张表中明确给出的记录与字段 UUID。项目 UUID、读取修订、捕获时间、
显示名称、类型与单位随内容保存；后续焦点、排序、改名或删除都不改变已经捕获的选择。
缺失对象保留诊断，已属于其他表的对象拒绝捕获，不静默改选对象。

捕获只读取选中范围的字面量、引用/公式定义和已有求值缓存。不为上下文计算而遍历未选中的依赖，
也不自动读取文件、日志、大型科学数组、程序源代码或连接凭据。文件路径和摘要不能代表完整文件副本。

范围限制为 1–100 行、1–64 列、最多 1000 个单元格；单项内容限 16 KiB，上下文限 256 KiB。
超限内容保留省略原因、大小和校验和；缓存缺失或损坏有独立诊断，不把省略内容当作已捕获。
这些限制约束读取与保存规模，不靠先读取整个项目再裁剪。具体字段和返回形式见[使用指南](../project-contexts.md)。

捕获对象不可变。项目修订继续推进后，旧对象保留来源修订；明确重新捕获产生新身份，
不在后台刷新、替换旧消息引用的内容。未来文件附件与运行摘要需要单独定义内容身份、预算和恢复语义。

## 消息与可执行提案分开

每条消息是引用一个已保存上下文的不可变文字记录，角色仅为 `user` 或 `assistant`，不表示经认证的身份。
普通文字、Markdown、代码块或模型声称的“已批准”都不能直接变成操作，也不会交给 Python 控制台执行。

提案来源记录引用消息、上下文和已保存草案，要求项目身份一致且上下文来源修订等于草案基础修订。
每个草案最多有一条来源记录。上下文用于解释修改依据，其选中范围不是草案命令的授权范围；
命令仍由已有预览、差异检查、修订校验与显式应用控制。

关联不会应用草案，也不会替换草案内容或回执。准备运行和提交任务继续采用各自接口和记录，
不能混入表格命令数组。本轮不保存待恢复的模型调用，也没有隐式生成或执行入口。

## 幂等与恢复

上下文、消息和来源关联分别使用调用者保留的 UUID。同一身份及相同请求返回原记录，
同一身份改内容会冲突。响应丢失时按 ID 或关联查询核对记录，再决定是否明确重试原请求。
记录保存在项目数据库中，不提升表格修订，也不进入表格撤销栈。

关闭重开可以恢复原数据与关系，不能自动捕获、调用模型、应用修改、运行代码或提交计算。
应用回执仍引用原草案；撤销表格修改不重置回执，不能把“已记录消息”或“已关联草案”当作“已应用”。
升级使用已有备份优先事务，格式 1–6 可显式升级到 7；旧项目打开时不自动迁移。

验收应覆盖固定选择与内容、大小/缺失诊断、跨表拒绝、同一基础修订关联、请求重试与身份冲突、
编辑后历史保持、重开不执行，以及格式迁移/备份。原生入口还需覆盖已有输入保护、过期回调丢弃、
草案来源刷新和不确定响应恢复；测试结果在开发计划中单独记录。

## 后续模型集成

以下是**尚未实现的请求生命周期提案**。当前格式 7 只提供上下文、消息与草案来源关系，
没有模型请求存储、提供方适配器、远端结果查询或取消接口。本节不增加可调用方法，
也不冻结格式 8、数据库 DDL 或提供方协议；实现前需按迁移与桥扩展规则另行审查。

### 请求身份与明确输入

首包限制为一次明确请求引用一个已保存上下文和一条用户消息，返回一条助手消息；
后续才接结构化修改提案。不会因打开讨论页、切换选择、保存消息或恢复项目而自动发送请求。
用户发送前可以查看将要引用的上下文、来源修订、缺失/省略信息及文字。未选入的历史消息、
当前实时表格、文件内容、运行日志和其他项目不自动补入请求。

发送意图先持久保存，调用者保留稳定的请求 UUID。不可变请求至少关联项目 UUID、上下文 ID
及内容标识、用户消息 ID、明确的文字输入、提示模板/适配器版本，以及实际发送内容的规范化摘要。
同一请求 UUID 和相同内容的重复保存返回原记录；改变输入、上下文、模型或生成参数时建立新请求，
不覆盖旧请求。再次生成使用新 UUID，并可记录它替代或重试哪个请求。

提供方来源记录包括提供方类型、配置的逻辑标识、请求的模型名称、生成参数与输出限制；
若响应提供实际模型版本、远端请求 ID 或用量，也保存这些观察值。记录配置的当时取值，
不能只引用以后可变的配置名称。项目内不保存 API 密钥、认证头、带凭据的 URL 或其他认证材料；
凭据在实际发送时从本机配置取得，不进入请求摘要、导出、错误文本或日志。

发送内容使用所选上下文的保存版本，保留省略与缺失标记；上下文已旧也不会自动换成当前值。
提供方输入预算不足时在发送前报告，不能静默截断或改选数据。消息大小继续服从现有 64 KiB UTF-8
存储限制；响应超限或格式不合法必须明确失败，不把截断的半条消息或半个命令当作完整结果。

### 状态与发送边界

持久消息、模型请求、修改草案和应用回执分别表达不同事实。建议的请求状态如下，
状态名称用于设计讨论，最终公开字段仍需在实现时定稿：

| 状态 | 表达的事实 | 后续处理 |
|---|---|---|
| `pending` | 请求意图已保存，尚未进入任何发送尝试，能够证明没有发出 | 用户明确开始，或在发送前取消；重启不自动发送 |
| `running` | 当前本机执行器已经取得该请求的执行权并进入发送/接收阶段；不等于远端已接受 | 接收结果、请求取消，或在失去执行器/结果证据时转为不确定 |
| `completed` | 完整有效的响应及其助手消息关联已经持久保存 | 查看结果；是否创建草案和是否应用仍是后续明确操作 |
| `failed` | 已知本次尝试失败，例如发送前校验失败、确定的远端拒绝、完整响应未通过本地格式/大小校验 | 保留失败阶段与证据；用户检查后可建立新的请求 |
| `cancelled` | 发送前已经取消，或已获得足以证明远端取消完成的终态证据 | 保留记录，不恢复生成、不发布迟到内容 |
| `uncertain` | 已经可能发送，但无法确定是否被接受、仍在执行或已产生结果 | 明确查询/核对已有请求；不能当作未发送，也不能自动重试 |

本机状态变更需要条件更新，同一请求只能由一个执行器取得发送权；重复点击不能派生第二次发送。
必须先记录进入发送阶段，再执行外部调用。若恰好在这两步之间崩溃，重启后也按 `uncertain` 处理：
记录不能证明网络调用没有发生。`pending` 只用于尚未跨过这个边界的记录，不能作为超时后的默认回退状态。

网络断开、等待超时或本机中断都不证明远端失败。保留最后观察阶段、时间以及已知的远端请求 ID，
有证据时区分远端拒绝、本地响应校验失败和本地保存失败；没有证据时不能写成确定的 `failed`。
本机请求 UUID 的幂等性不等于提供方执行幂等。适配器必须说明是否支持按 ID 查询或幂等提交，
不能用一套未经确认的自动重试策略覆盖不同提供方。

### 结果保存、取消与迟到响应

请求在创建时固定用于助手消息的身份，接收结果时核对请求 UUID、原项目及执行器代次。
同一完整结果重复到达只完成一次本地保存；相同请求返回互相矛盾的完整结果时保留诊断，
不覆盖已完成消息。消息保存与请求完成标记需要原子提交，或具备可重复执行的本地收尾过程：
已经保存的消息可按固定 ID 找回并补齐关联，不能因为收尾失败重新调用模型。
若采用分段提交，尚未完成关联的响应只能作为请求输出暂存，不能提前发布为助手消息；
取消与最后发布必须检查同一个请求状态，避免已经确认取消后又因本地收尾发布内容。

流式片段只用于显示进度，不是可执行提案，也不覆盖已有不可变消息。完整响应通过校验并保存后，
才能成为 `completed`。若进程在收到响应后、完成持久保存前退出，恢复需核对已有本地记录和远端结果；
仅凭曾经显示过一些文本不能推断生成已完成。

取消首先记录用户的取消意图并停止后续本地派发；如果适配器支持远端取消，再发送一次对应请求。
取消意图和终态分开保存，不需要用新的请求状态去表示每一个网络步骤。仅关闭流或停止本机等待，
而不能确认远端状态时，结果应为 `uncertain`，同时保留取消意图，不能声称远端已经停止。

完成与取消竞争时以持久记录的条件更新决定本地先后：

- 已经完成保存的结果保持 `completed`；稍后的取消不撤销助手消息，更不撤销已明确应用的项目编辑。
- 已确认取消的请求保持 `cancelled`；迟到响应只记录为诊断，不发布为新消息或草案。
- 已请求取消但仍不确定的请求，可以通过后续查询或经过身份核对的完整响应确认最终结果；
  即使核对为完成，也只关联回原请求并标明取消意图，不抢占当前输入、切换页面或执行提案。
- 项目已关闭、切换或桥已重启时，旧代次的 UI 回调不能更新新项目或覆盖正在输入的文字。
  持久结果只能写回已绑定且重新校验身份的原项目，不能使用此刻的“当前项目”替代目标。

### 重启后的核对

打开项目先展示已保存记录，不恢复网络生成或工具执行。`pending` 等待再次明确开始；
旧执行器留下的 `running` 在没有活跃执行器可核实时显示为 `uncertain`，不能继续显示为正在接收。
已有完整助手消息但缺少本地完成关联时，可以用固定 ID 核对并完成本地收尾，不产生外部调用。

用户明确刷新不确定请求后，若提供方支持查询且已有远端请求 ID，只查询那一次尝试；
将仍在运行、已完成、已取消或确定失败的观察记录下来。没有查询能力、请求 ID 丢失，
或查询暂时不可达时，保留不确定状态及原因，不把“查不到”直接解释为“从未执行”。
用户可以明确放弃等待并另建请求，但旧记录仍保留，不把新请求冒充旧请求的安全重放。

### 模型文字、工具提议与草案

首包只发布文字，不开放工具执行。之后的结构化输出分成独立的文字与操作提议，
不能从 Markdown 代码块、自然语言中的“请执行”或“已批准”推导出命令。
第一种可接入的提议只允许已有普通项目编辑命令；模型提供的项目 ID、候选快照、应用回执或审批声明
均不能替代本机已有记录。执行 Python、准备运行和提交任务继续是各自明确的操作，不混入编辑命令数组。

用户明确选择检查/保存提议后，复用已有 `preview` 和 `drafts.save`，基础修订固定为原上下文修订，
校验通过后保存稳定命令；以固定的草案/来源关联 ID 记录本次提议，复用现有格式 7 的消息与草案关系。
助手消息完成不要求草案也保存成功。生成期间项目发生变化时，消息仍可保留在原上下文下，
但旧基础修订的草案保存/应用应冲突；不能只提高修订号后重试。需要新数据时明确捕获新上下文并重新核对方案。

来源记录说明提议参考了哪份数据，不证明其命令只修改选中单元格，也不构成用户授权。
已有草案或正在输入的文本仍受原生检查保护。最终应用仍由用户明确发起，并保留当前原子应用回执、
普通撤销及“撤销不重置旧回执”的规则；恢复模型请求不会走应用入口。

### 分步实施与验收

1. **先验证本地生命周期。** 使用不联网的可控适配器，定义请求查询、明确开始、取消和恢复行为，
   覆盖重复点击、发送边界崩溃、确定失败与不确定结果。请求存储位置、迁移策略及桥扩展在此阶段定稿，
   不能先借现有消息表伪装请求状态。
2. **再接单一提供方的文字响应。** 明确输入/输出预算、凭据读取边界、远端查询/取消/幂等能力，
   验证完整文字保存与受限流式进度。只展示结果，不开放任何模型触发的项目或 Runtime 修改。
3. **接普通编辑提议。** 通过已有预览、保存草案、来源关联和明确应用完成闭环；
   先验证项目已变化、格式错误和已有输入冲突，再考虑其他独立工具类别。

各阶段应通过以下行为验收，测试不依赖真实密钥或不可控网络时序：

- 请求使用固定上下文和配置快照；后续表格、配置、选择变化不改写原请求，凭据不进入记录、摘要或日志。
- 同一 UUID 的重复开始只触发一次适配器发送；不同输入复用 UUID 被拒绝。发送前后各个崩溃点均可解释，
  重开不自动发送；超时不能误标为尚未发送或确定失败。
- 取消先到、结果先到、迟到结果、重复片段及桥重启均不覆盖其他请求或当前输入，
  不产生重复助手消息、草案或应用；未知远端结果持续显示不确定。
- 完整响应与本地保存之间中断后可按固定身份核对；超大、非法或不完整响应不会变成有效消息/命令。
  不支持结果查询的适配器保持可诊断边界，不假装具备恢复能力。
- 编辑提议使用原上下文修订，过期方案不被自动重定位；查看、保存、恢复消息或提案均不改变表格或任务。
  明确应用后可正常撤销，旧应用回执仍防止重放。

多上下文历史组装、上下文压缩、文件附件、任意工具循环及多设备会话同步留给后续独立设计，
不作为首个文字请求闭环的前置条件。

# 草案、对话上下文与恢复边界

状态：2026-09-29。格式 6 的[持久草案与应用回执](../project-drafts.md)已实现；
本文的对话、上下文捕获及消息关联是下一阶段提案，尚无存储格式、桥方法或模型服务实现。

## 当前可复用的基础

普通项目命令共用 `apply` 与只读 `preview`。原生检查展示确定性差异和公式错误；
`stk.project.review` 可以把 Python 提出的命令送入该视图。持久草案保存稳定命令、项目 UUID、
基础修订及终态回执，不保存整份项目、模型上下文、差异快照或审批身份。

保存不更改参数；应用参数修改、准备运行方案和提交计算分别由明确操作触发。
重开项目不执行草案；已有回执不会因撤销参数而恢复为待执行状态。这些边界保持不变。

## 下一步：显式上下文捕获

先实现不依赖模型的上下文检查入口，让用户明确选择本次讨论引用什么，再考虑提供方适配：

- 固定项目 UUID、读取修订、捕获时间，以及明确选定的表格/字段/记录 UUID。显示名称用于阅读，
  稳定 ID 用于关联；后续焦点或排序变化不改变已经捕获的选择。
- 按明确范围保存类型、单位、当前值、引用/公式及错误摘要；显示包含项、缺失项、截断原因与大小。
  不默认把完整数据库、全部日志或大型科学数组装入上下文。
- 文件、运行和结果引用保留其稳定 ID 与已捕获版本；路径或摘要不能代表完整内容快照。
  用户选择附带内容时，记录内容身份、大小与来源。保存连接身份不附带认证凭据。
- 将捕获对象作为不可变版本关联到具体消息/提案。项目继续修改后保留原版本，显示已过期，
  明确重新捕获产生新对象；不在后台替换旧上下文。

候选捕获结构至少包含 `project_id`、`source_revision`、选中对象 ID、内容摘要和限制信息。
最终字段、总量上限、文件内容策略和协议版本须在实现前定稿，不能把本节作为可调用接口。

## 消息与可执行提案分开

对话消息表达问题、说明和推理过程，可关联一个上下文版本。结构化提案引用该上下文及生成它的消息，
并持有明确的动作类别。普通文字、Markdown、代码块或模型声称的“已批准”不能直接变成项目操作。

项目编辑提案仍使用普通命令与原基础修订，并进入原生差异检查。必要时关联到格式 6 草案 ID，
不允许模型伪造已计算快照或应用回执。准备运行和提交任务采用各自接口和记录，不能混入表格命令数组。
对模型生成代码的执行入口另行设计，不把输出的 Python 自动交给控制台。

持久消息不代表持久运行中的请求。应分别记录生成请求、返回消息、提案保存和显式应用的结果；
先支持用户手工填写或导入消息/提案，验证重开及来源关联，再接模型。

## 恢复与验收条件（待实施）

每次生成/保存请求拥有调用者保留的身份。超时或重启后先查询记录，区分尚未开始、进行中、
失败、已返回和结果不确定；不得因缺少本地响应再自动提交计算。回执必须引用原提案，
并区分应用成功、后来撤销、当前项目已继续变化；不把“已生成”当作“已应用”。

首个可交付包应证明：

1. 选择一组参数行并捕获上下文，切换选择或继续编辑后，原上下文仍可查看并显示来源修订。
2. 手工消息关联到该上下文，结构化提案可保存为草案，原生界面显示其来源并继续显式检查。
3. 关闭重开恢复消息、上下文与提案关联，不能自动重新生成、应用或提交任务。
4. 重复保存请求返回同一记录；过期/缺失对象可诊断，不能静默绑定到新对象。
5. 参数应用与运行准备、提交的记录相互独立，各自的错误和不确定状态可查询。

模型提供方、密钥配置、流式响应、工具调用、上下文压缩及多设备会话同步另行设计与验收。

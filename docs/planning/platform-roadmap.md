## 1. 首期目标与退出边界

试点选定一个研究问题、一种专业软件/执行器、一套公开或获准使用的数据和一个明确支持的部署组合。
STK 为主体，Core 与云端运行同一后端代码、领域规则及任务状态机；Desktop 保留 C++ / Python 原生交互，React Web 提供对话、轻阅读和任务入口。
两端采用相同命令与回执规则，不能用两个独立可写的业务后端拼出合并效果。

首期目标是：Web 显式提交 → 授权节点执行 → 断线/换登录终端继续追踪 → 获准产物交接 → Web 预览与原生完整结果。
真实许可软件和 GPU 是该主链的目标能力，但只有软件、许可、设备和节点支持都具备并实际通过时，才能将它们列入本期已验证出口。
资产不满足时，可以完成协议子集，整体真实主链仍记为阻塞，不能降低名称或改用 stub 后宣布完成。

| 首期必须争取完成的范围 | 首期不包揽的范围及去向 |
|---|---|
| D1 同修订共同后端的本地/云端装配与契约比较；D2 一条 Linux 优先的跨端任务链 | D1/D2 的所有业务、调度器和部署形态仍按增量扩展 |
| D3 选定一个领域纵切面，保留身份、历史回执、当前授权和唯一写入归属 | 对话/生成账本、科研记录/独立复核、文献等全部迁移不压进单个切片；未选项保留台账 |
| D4 在早期核准真实资产后，争取一个许可软件 + GPU 后处理组合；原生完整结果和草稿保护 | Windows/macOS 全功能节点、所有 GUI 软件、完整 PDF 标注/协同编辑、多 GPU/MPI、远程桌面分别验收 |
| D5 试点安装/版本清单、升级兼容和回滚演练的必要准备 | 全平台干净机/离线发行、商用托管配额、插件商城及交易后置，不把打包成功当完整发行 |

没有实测的功能始终标为“未验证”。工程功能可用、实际设备执行、科学有效性分开报告；
求解器退出 0、摘要一致或界面预览成功，不等于研究问题得到有效回答。

## 2. 责任与产能假设

下面是**角色需求，非已确认人数或投入**。供排期讨论的假设为三类持续工程负责人：共同后端/执行、原生桌面、React Web；
另有共享的测试/运维支持，以及合作方科学负责人和资产管理责任人。角色可以兼任，不能将同一个人的时间按多份并行产能计算。
若只能串行投入或缺少独立验证支持，应减小切片或延长周期，而非维持同样范围承诺。

| 责任角色 | 负责的结果 | W0 必须确认 |
|---|---|---|
| 平台技术负责人/集成人 | 共同后端边界、版本/身份、跨仓库集成、迁移与回滚 | 实际负责人、可用投入、架构争议的决定人和审阅替补 |
| 后端与执行负责人 | 应用服务、当前授权、持久回执、节点/任务/资源准入、数据交接 | 是否与技术负责人兼任；执行器和数据库适配的实际能力 |
| Desktop 负责人 | 原生任务入口、Viewer/草稿、完整结果；PDF/会话后续路径 | C++ / Python 支持、可用平台和真实窗口验证设备 |
| Web 负责人 | React 对话/文件/任务入口、换端恢复、有限预览和真实点击证据 | 接口与版本协作方式；是否承担旧服务兼容适配 |
| 测试/部署责任人 | 隔离环境、故障注入、证据、CI、受控试点安装及资源收尾 | 可用验证投入、独立复核人、机器维护和运行时段 |
| 合作方科学负责人 | 问题、参数、单位、参考结果/容差、科学判据和复核 | 有权确认口径的人员、反馈窗口、可公开/可共享范围 |
| 合作方资产责任人 | 软件/许可、GPU、节点、必要 GUI 会话和受限数据 | 实际可用性、访问方式、使用范围、维护/停机窗口 |

W0 记录每人的实际可投入时段及已有维护负担，不预造精确人天。每周最多承接有明确负责人、输入和验收人的工作；
未完成项计入下周负荷。W2 用已验收切片、返工、阻塞时间和真实投入重排，不把代码行数、用例总数或会议次数当产能。

## 3. 仓库与交付责任

| 边界 | 首期责任安排 | 交付核对 |
|---|---|---|
| STK：`suan/`、原生 Desktop、`docs/specs/` | 共同后端基础、执行/数据服务、C++ / Python 交互和现有发布合同 | 旧 CLI/Bridge/Runtime 行为保持；新能力按 schema/版本增量进入，不导入归档代码 |
| Synthrix：React 前端与既有后端兼容边界 | 网页逐项改接共同应用服务；现有 TypeScript 领域逐项迁移 | 每个切片列当前唯一写入服务、旧接口退出条件、历史回执与授权差异，不能只改 URL 宣布完成 |
| 跨仓库协议与版本 | 技术负责人维护兼容矩阵；两端负责人共同确认接口 | 绑定两仓实际源码/构建、协议、依赖与配置；具体包发布和仓库整合方式在实现设计中确定，不预设搬仓 |
| 合作方资产与科学输入 | 合作方确认范围，工程侧使用批准的输入与环境 | 资产/科学材料与公开工程证据分开保管；公开文件只使用合成或获准材料 |

每次纵切面要有一个集成负责人和一个验收人。仓库分工不改变同一后端要求，也不表示两仓可以分别维护不同授权或状态规则。
实施交付仍遵守各仓现行检查、密钥扫描和 CI 顺序；不能把计划文档视作部署、模型调用或私有数据出站授权。

- [ ] 核对实施基线、既有 WIP 和 CI；冻结要保护的旧接口、项目格式与现有结果，不以旧绿灯覆盖新字节。

| W9–W10 / D4 选定能力 | 在已核准资产上将许可执行→GPU 后处理→Web 预览/native 完整结果接成链；做资源争用、数据损坏和取消。演示真实设备证据、单位/参考值与草稿保护 | STK 执行/原生 + Web 结果页；合作方提供许可、GPU、参考结果和科学复核 | 可提前做真实环境验证；缺资产只能提交 stub 协议结果，真实出口保留阻塞。完整 PDF/全平台不并入该两周承诺 |
| W11–W12 / 试点收口、D5 准备 | 回归本期切片、故障/恢复、隔离试点安装、版本绑定及回滚；合作方按固定场景试用。演示从新会话到原任务/结果重开，形成验收矩阵和后续排期 | 集成/测试主责，两仓交付清单；合作方提交逐项意见与科学结论 | 没有事实不结项；未过项带负责人/依赖/下一检查点延期。只称已验证配置下有限试点，不称完整 D5 或平台成熟 |

关键依赖链为：身份/合同与当前授权 → 唯一写入和持久回执 → 共同后端两部署 → 跨端生命周期 → 领域迁移/数据交接 → 真实能力闭环 → 试点发行准备。
Web/原生可并行准备界面，许可/GPU 可提前预检，但不能用并行 UI 开发抵消后端依赖。W4、W6、W8、W10、W12 以退出证据复盘范围；
延期先调整范围和资源，再更新时间，不能靠压缩科学验收或删除失败用例维持表面进度。

不新增本期 PET 业务字典、专项训练/部署或材料指标承诺。

## 8. 每周固定协作机制

建议每周一次 60 分钟协作会，固定星期/时间在 W0 由双方确认。平时异步更新同一行动与阻塞台账；只有跨仓依赖影响当前切片时增开短会。
所有会议材料均记录真实状态，不因演示成功自动通过验收。

| 固定议程 | 建议时长 | 产出 |
|---|---:|---|
| 上次行动与阻塞核对 | 5 分钟 | 完成证据、未完原因、影响的依赖 |
| 合作方问题/输入与科学口径 | 10 分钟 | 数据/资产变化、参考值/容差、需决定事项；科学结论单列 |
| 当周可运行演示 | 15 分钟 | 固定起点、真实点击/日志/回执/设备与结果；失败照实展示 |
| 结果与风险审阅 | 10 分钟 | 工程/真实执行/科学有效性分别判断；新增缺口、回归或隐私问题 |
| 范围、依赖与决策 | 10 分钟 | 接受/拒绝/延期的明确理由；资源/资产/兼容与回滚影响 |
| 下一周行动确认 | 10 分钟 | 每项一个负责人、验收人、输入、退出证据和下次检查点 |

**会前一个工作日**由各负责人提交：本周目标/实际、源码和环境版本、证据索引、失败/未验证项、合作方输入缺口、下周候选与需决定问题。
演示必须注明 live、录屏、原型或 stub；真实 UI 记录固定布局和实际点击，真实计算记录原任务/软件/设备与产物来源，
不得把合成模型响应称为模型效果，也不得用一次看得见的截图证明隐藏草稿或后端已完成。
会议结束后更新决定与行动台账；没有明确授权的问题保持待决定，不以无人反对、时间到或主持人口头推测作同意。

不得通过放松授权、绕过许可、删除用例或把 stub 改名来清除阻塞。不能解决的缺口带入周会，选择减范围、补资源或改时间，保留原记录。

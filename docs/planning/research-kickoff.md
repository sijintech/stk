# STK / Synthrix 科研平台启动会汇报稿

2026-11-06。用途：约 15 分钟主讲，之后讨论。汇报时长、实际人员投入、启动日期和首演日期尚未确认。
以下是可直接使用的讲述提纲；周数、人数需求和新仓库都是待核定的规划，不是交付承诺。
投屏版见[启动会演示文稿](research-kickoff.html)，技术依据为[总体框架](../design/platform-framework.md)、
[开发计划](platform-roadmap.md)与[仓库规划](repository-strategy.md)。公开材料统一称“合作方”。

## 1. 我们要共同交付什么（1 分钟）

**投屏要点：一个科研平台，共同后端，原生桌面与网页两个入口，多个执行节点。**

“我们的目标是把科研计算、前后处理、文献阅读和 AI 对话放进一个可追溯的工作流程。
STK 作为平台主体，保留 C++、Python 和 GPU 的原生能力；Synthrix 提供网页对话、轻量分析和研究管理入口。
计算可以发生在自己的工作站、实验室机器或云主机，尤其是已经具备软件许可的电脑。
用户换一个终端以后，仍然能找到同一个项目、任务和结果。”

本次会议希望确定首个试点问题、责任角色、可用资产和验收方式，随后每周用实际演示及证据推进。

## 2. 已有基础与当前缺口（1 分钟）

**投屏要点：已有模块基础；统一后端和完整跨端流程仍需实施。**

“STK 已有原生编辑器、Python 项目与科学服务、Linux Runtime/Hub/节点能力；Synthrix 已有 React 页面和独立后端。
这次工作是把它们整理成同一套后端实现，使不同入口共享业务规则。我们已完成架构、任务数据协议和验收设计，
但不会把文档完成算成系统已经接通。Windows/macOS 完整节点、原生 PDF 标注、真实许可与 GPU 链路也需要各自的验证。”

会上只将有来源和范围证明的能力称为已有；本次规划没有运行新产品验收。

## 3. 总体架构如何组成（2 分钟）

**投屏要点：入口 → 接口适配 → 共同应用服务 → 节点执行 → 数据与硬件。**

“Core 和云端不是两份后端。它们来自同一套代码，区别在于部署角色、启用模块、存储适配和可用执行器。
桌面使用原生 C++/Python，网页使用 React，都调用共同服务。服务器可以只安装无界面 Core，
工作站可以同时安装 Core 和 Desktop。三维交互留在原生前端，项目修订、任务、数据身份和权限由共同后端负责。
这样既保持本地性能，也让网页能够调度已连接节点。”

讲解[总体框架图](../design/platform-framework.md#五层框架与两个部署位置)。强调本地已授权独立工作可离线，
云连接失效不会把原任务自动复制到另一台机器重新运行。

## 4. 第一条展示链路（2 分钟）

**投屏要点：网页提交 → 原节点执行 → 换端追踪 → 网页预览 / 原生完整结果。**

“首先选择一个小而完整的研究场景。网页明确提交冻结的输入，任务在指定节点执行。
关闭网页后，另一终端还能按原任务 ID 查看状态和日志。输出经过校验，网页展示轻量结果，STK 打开完整数据。
真实许可软件和 GPU 后处理会在环境就绪后接入同一条链。我们会主动断开连接、重复投递请求和请求取消，
验证同键重投保持同一任务，响应不确定时不自动另起执行，失联保持待核实。”

这里展示的是目标流程图；在完整验收前，不用模拟视频或逐端 mock 冒充实际闭环。
若唯一软件依赖尚未支持的 Windows GUI 节点，先重估节点工作量，不假定 Linux 可以替代运行。

## 5. 三个贯穿研发的约束（1 分钟）

**投屏要点：唯一任务事实、数据留在合适位置、科学结论单独验证。**

“相同项目和任务只有明确的写入归属，所有入口使用同一身份；原件和文献索引默认留在所属节点，
需要传输时明确范围和目的地。软件运行结束、文件校验成功和科学问题得到正确结果是不同层次，
我们分别记录。合作方负责提供或确认科学问题、参数、参考值和复核口径，工程团队负责可靠执行、数据来源和交互。”

连接账号不扩大文件、桌面或外部模型权限；现有待决项目保持，不由这次架构提案隐含批准。

## 6. 仓库如何协同（2 分钟）

**投屏要点：两个现有产品仓库 + 按门槛新增的集成发布仓库。**

“STK 仓继续维护共同后端、原生桌面、CLI 和正式协议。后端和桌面目前联系很紧，先在同仓模块化，
方便原子修改和兼容验证。Synthrix 仓保留 React，旧 Node 后端按领域逐步迁移退出。
当跨仓组合需要反复发布时，再建立或复用集成发布仓，候选名称为 stk-platform，锁定两仓的确切版本并做组合验收。
插件和受限研究资料按独立维护、许可及权限需要再安排，不先建立一批空仓。”

仓库数量不决定后端数量；共享代码通过正式包和版本消费，不复制后端目录。
协议在 STK 保持一个权威来源，网页先锁定 SDK 版本，组合清单再绑定源码 SHA、制品摘要和验收证据。
本轮未创建或重命名任何仓库。

## 7. 条件性的 12 周试点安排（2 分钟）

**投屏要点：每两周一个可验收输出，W2 按实际投入校准。**

| 周次 | 会议上应看到什么 |
|---|---|
| W1–W2 | 试点输入、责任与资产清单；最小无 GUI 装配和许可/GPU 预检结果 |
| W3–W4 | 同一后端在本地/云配置运行；同命令规则与旧接口兼容证据 |
| W5–W6 | Web/CLI/Desktop 一条真实任务链；换端、断线、取消与结果 |
| W7–W8 | 一项选定 Synthrix 领域迁移；身份/历史回执/授权及回滚 |
| W9–W10 | 资产就绪时的真实许可/GPU 链；原生完整结果和科研参考对比 |
| W11–W12 | 合作方试用、故障回归、有限配置安装与版本/回滚清单 |

“这是一份有限试点的候选安排，需要后端、原生桌面、网页等持续工程责任，以及测试运维与科学资产支持。
这些角色不等于已确定的人数，同一个人兼任不能算多份产能。第二周结束后，我们根据真实投入、阻塞和已完成证据重排。
完整多平台、全部科研领域、PDF 协同、MPI、商城和完整发行继续保留，不塞进这 12 周承诺。”

## 8. 前两周立刻准备的工作（1 分钟）

**投屏要点：一个问题、一个环境、一套输入输出、一个可验证的最小后端。**

“工程侧先核实施版本与现有失败，列出要保护的接口，完成最小共同后端装配和固定任务身份设计。
合作方同步给出一个试点研究问题、软件与许可、实际机器和数据可用范围，确认单位、参考结果及验收人。
两周末拿实际预检和最小操作演示决定后续排期；未到位的依赖明确列出负责人和检查点，不把它们隐藏到最后。”

详细执行清单见[W1/W2 清单](platform-roadmap.md#6-w1--w2-的具体工作清单)。

## 9. 每周会议怎样推进（1 分钟）

**投屏要点：会前给材料，会中看证据，会后落责任。**

“建议固定每周一次约 60 分钟，具体时段由双方确认。会前一个工作日更新目标、实际结果、失败、证据和需决定的问题。
会上先看上周行动和科学输入，再看可运行演示，最后确定下一周最小切片。
演示标清 live、录屏、原型或 stub；每项行动有负责人、验收人、输入和检查点。
科学结论、工程功能和真实设备验证分别报告，阻塞通过调整范围、补资源或改时间处理。”

可直接复用[周报、行动及决定模板](platform-roadmap.md#8-每周固定协作机制)。

## 10. 启动会需要形成的决定（2 分钟）

1. **试点场景**：研究问题、软件/执行器、输入/输出、参考结果和验收人。
2. **资源与责任**：各角色实际投入、可用节点/许可/GPU、资产缺口和补齐时间。
3. **首期范围**：选定一个 D3 领域切片，明确条件性的真实能力门和后置项目。
4. **协作方式**：周会时段、证据/行动台账位置、跨仓负责人；达到门槛再决定集成仓名称和维护权限。

“启动会结束时，我们需要的是一份有负责人、有输入、有验收标准的前两周清单。
后续每周都让大家看到同一条研究流程向前推进，并保留失败和未知，逐步形成可使用、可追溯的科研平台。”

本次不要求会议代替既有 S3/MuPRO 口径、S2c 权限及分析修改提案等未决事项的专门决定。
部署、付费模型调用、真实私有数据出站和新仓访问授权不由汇报稿隐含批准。

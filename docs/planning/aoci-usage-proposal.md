# 提案：把 AOCI 从强制前置降为按需工具

状态：**root 审阅通过，决定以修订后的提案合入；P1/P2 尚未生效**。
本次授权是审阅并决定文档是否合入；取消强制预读和改变维护频率仍需另行决定及修改仓库规则。
当前仍按 [AGENTS.md](../../AGENTS.md) 与已启用工具的运行合同工作。

- **起因：** 所有者在 2026-11-08 要求评估"有没有必要使用 AOCI"，并要求写成提案。
- **作者：** Claude（`stk-claude` / `claude/support`）。
- **审阅：** root，2026-11-08；原提案提交 `1a5dc3ad1848c21a4345a847ee08e9a0f841575e`。
- **数据时间：** 作者观测截至 2026-11-08 17:02Z；下文另列 root 在 `bcec982b` 上的复核快照。
- **结论：** 当前强制使用方式有明确开销，尚无同类任务对照证明这些开销带来相称的质量收益。建议保留 AOCI 作为按需导航工具，把维护集中到里程碑。这个判断限定于本仓库的长期并行开发方式。

## 1. 现行规则

以下规则来自 `AGENTS.md` 的 AOCI 区块；行号仅对应作者核查版本：

- **新会话强制整份读取：** 没有可靠认知时，必须先 `aoci_rules` 再完整 `aoci_overview`（`AGENTS.md:121`）。
- **上下文压缩后强制重读：** 任何上下文压缩之后，此前的认知一律视为不可靠，必须用 `context_compaction` 重新完整读取，并提交一次 Attestation（`AGENTS.md:125`、`:149`）。
- **分块读取期间不得旁读：** 必须跟着 `next_cursor` 一直读到 `completed=true`。Attestation 完成之前，不得用源码、Memory 或检索来补充认知（`AGENTS.md:131`）。
- **每次交付都要维护：** 受管对象一旦变化，每次任务收尾都要 `aoci_maintain`，再按候选提交 `aoci_update_entry`（`AGENTS.md:159`）。

## 2. 实测成本

作者统计了一份本机 Codex 会话日志和当时的仓库状态。原始会话日志不随提案发布；root 没有重读日志来复算调用数量及字符比例，因此这两项保留为**作者报告**。仓库字节、提交计数和目录占用已另行复核。

| 作者报告的 AOCI 工具输出 | 约 292.6 万字符，占全部工具输出约 1523 万字符的 **19%** |

**计法：**
- "显式 AOCI 调用"指参数中含 `aoci_overview`、`aoci_maintain`、`aoci_update_entry`、`aoci_rules` 等工具名，或 `aoci index/verify/check` 命令的调用；输出按这些调用的返回内容计。
- 仅仅在路径中出现 `.aoci` 的普通 git 命令不计入。**19% 只是所选输出的字符占比**，不能换算为总耗时、模型计费 token 或费用占比；聚合工具调用的拆分口径也会影响调用次数。
- AOCI 的 token 数是机器按字节量估算的传输规模，不能当作模型实际 tokenizer 或账单读数。46 块和 1216 条来自本次真实传输，不代表每条语义都已用源码重新验证。
- 仓库提交计数使用 `git log --since=2026-10-08 --format=%H HEAD` 及相同命令附路径过滤；按当前主线计数，不混入全部 refs。触及索引的提交可能同时交付产品代码，不能把 35 个提交都当作纯治理工作。
- 目录占用随本地事务增加；容量统计不能证明其中哪些文件可以安全删除。

**由此产生的结构性问题：**

1. **重读有自我循环风险。** 一次完整传输规模较大，而压缩后的规则又要求重新传输。这个组合会挤占开发上下文；当前数据没有单独证明某一次压缩由重读造成。
2. **状态文档被治理记录稀释。** 交接和验收记录里大量篇幅是 "Dirty/Stale、Challenge 10/10、Attestation、维护批次"。读者要从中分辨哪些是开发进展、哪些是索引治理，交接成本因此上升。
3. **多 worktree 需要各自接线。** 收据绑定仓库根，root 的收据不能冒充 Claude worktree 的认知，这是必要的隔离边界。当前协作要求报告绑定差异并使用该工作区的受支持入口（见[协作约定](agent-collaboration.md)）；这一接线成本不能推导为 AOCI 不支持多 worktree。
4. **本地状态持续增长。** 事务目录已约 605 MiB；本提案尚未核实工具支持的保留或清理流程。

## 3. 可观测的收益

- **设计目标合理：** 帮助新会话建立架构地图，并保存一些不显眼的约束；受管条目当前为 1216 条。
- **证明范围有限：** 交付确认和 Challenge 能核对交付身份及抽样对象、标签和职责匹配，不能代替源码审查、运行验证或缺陷率评价。Dirty/Stale 时尤其不能把条目当成当前实现的证明。
- **作者报告的任务样本：** Claude 未依赖完整 AOCI 预读，通过有界 `rg` 和 `sed` 完成以下工作，并引用到具体 `文件:行`：

- **这次交付和这些审阅发现了几项被采纳的真缺陷：**

  - Hub 缺少单实例锁。
- 这些样本说明具体审阅可以依靠源码与契约完成，但没有控制模型、角色、任务难度和既有上下文，不能证明索引没有收益。"没有观察到因缺少索引而出错"限于作者参与的这批工作。

## 4. 提案

### P1：取消强制的整份读取，改为按需查询

- **新会话：** 先读 `AGENTS.md` 和 `handoff.md`。需要系统全貌时，才调用 overview；平时按任务范围使用 scope 或单条条目查询，或直接读源码。
- **上下文压缩后：** 不再强制整份重读。会话按交接摘要继续；必要时只重读与当前任务相关的条目。
- **取消日常任务的前置门：** 源码调查不应被强制启动的完整认知链阻塞。若主动运行正式 Overview/Attestation，仍遵守该次工具合同；不得把局部读取或交接摘要宣称为完整交付，也不旁路未决 Recovery、CAS、冲突或审批边界。

建议改写后的规则，可以替换 `AGENTS.md:121-155`：

> AOCI 是可选的导航工具。需要了解不熟悉的模块、跨模块关系或非显然约束时，按范围查询相关条目，或在必要时读取完整索引；
> 结论以当前源码、发布契约和实际测试为准。上下文压缩后不要求整份重读；按交接记录和当前任务范围恢复。
> 主动请求正式认知交付时遵守其交付和验证合同，并如实说明覆盖与新鲜度；Recovery、冲突、CAS、审批及凭据边界继续有效。

### P2：维护改为里程碑批量进行

- **取消逐次维护：** 不再在每次交付时执行 `aoci_maintain` 和 `aoci_update_entry`。
- **改为批量维护：** 在 root 定义的里程碑执行一次，例如一个功能系列合入后、发版前或每周一次。批量维护照旧按 AOCI Guide 执行，保留其候选、证据和事务约束。
- **Dirty/Stale 的含义：** 在两次维护之间，索引处于 Dirty/Stale 是预期状态，不构成交付的阻断项。

### P3：状态文档不再记录 AOCI 治理细节

- 四份状态文档只记录开发、测试和 CI 事实。
- AOCI 的维护结果留在 `.aoci` 自己的 ledger 和回执中。状态文档里每个里程碑最多一句"索引已于某提交维护"。
- 这适用于后续记录，不清除历史或既有 WIP。未决写入、Recovery、冲突和安全续接仍须留下必要状态与证据位置；不把正式 Whole-Index 正文复制进交接。

### P4：给本地事务数据设定保留期限

- 由 root 先确认当前工具支持的流程，以及事务是否仍被恢复、审计或未决写入引用，再评估保留期限；不能仅按文件年龄批量删除。
- 本文不删除任何文件。

### P5：可选，做一次小规模对照

如果希望用数据而不是判断来决定，可以选两到三张同类任务卡（例如 D1 故障场景），分别"使用 AOCI 整份读取"和"按需读取源码"来完成，比较以下几项：

| 指标 | 说明 |
|---|---|
| root 审查发现的缺陷数和严重程度 | 衡量质量 |
| 返工次数 | 衡量一次做对的比例 |
| 消耗的 token 和墙钟时间 | 衡量成本 |

这属于工程试运行，少量任务没有明显差异不能证明两种方法等效。应记录模型、基线、任务类型和实际交付，结合返工与成本决定后续使用；本次文档合入不以试验为前提，试运行也不能擅自绕过现行规则。

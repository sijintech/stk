# 保存与恢复项目修改草案

格式 6 增加持久项目草案：保存一组经过预览校验的普通编辑命令，关闭项目或重启桌面后，
再显式载入、检查和应用。项目数据仍由同一个编辑引擎修改；保存草案不会修改表格、提升编辑修订、
准备运行或提交任务。格式 7 已另行提供[项目上下文与讨论记录](project-contexts.md)；当前没有模型调用或审批快照。

新建项目使用格式 8；草案接口最低需要格式 6。已有旧项目须通过“备份并升级项目”、`store.upgrade(expected_revision=...)`
或 `stk.project.upgrade(expected_revision=...)` 显式升级；升级先创建并校验数据库备份。
打开项目不自动迁移；旧格式调用草案接口返回 `unsupported`。迁移和备份边界见[项目存储指南](project.md)。

## 原生界面

在项目表格的“修改检查”页使用[原生预览](project-preview.md)，然后展开“已保存草案”：

1. 输入名称，点击“保存已检查草案”。仅当前修订上的有效预览可保存，保存的是包含稳定 UUID 的
   实际候选命令。不会自动保存未完成的 JSON 输入，公式错误仍按普通预览规则展示，不会被自动修复。
2. 关闭再打开项目，进入检查页并展开面板。列表按需读取，显示名称、基础修订、待处理/已应用/已丢弃
   状态及应用修订；每页最多 100 条。跨客户端的更新需要明确“刷新保存列表”。
3. 选中待处理草案并点击“载入待处理草案”。已有输入、候选或错误时，先明确“清除草案”，防止覆盖当前工作。
   载入恢复稳定命令与保存时的基础修订，随后必须点击“计算预览”，查看重新计算的差异和公式错误。
4. 基础修订仍匹配时，明确点击“应用已检查的修改”才提交。数据修改与草案“已应用”回执在同一个事务中保存。
   在项目表格中撤销可恢复数据，但不会把该草案改回待处理或再次执行。
5. 不再需要待处理草案时，点击“标记为已丢弃”。记录保留以便查询，不能再应用。

项目已变化时，原草案不能直接预览或应用。可明确选择“以当前修订另起草案并检查”：保留原保存记录，
把命令复制为未保存草案并在当前修订重新计算。再次核对后可以保存为新记录；复制后可能因对象变化而校验失败。
修改载入命令的文本也会解除与原保存记录的绑定，形成未保存副本，不更改原记录。

“清除草案”只清空当前编辑器，不会废弃数据库记录。切换/关闭项目或桥重启清除当前候选及载入状态；
保存记录仍在。重开后不会自动载入、重新预览或应用。保存与应用的迟到响应不会覆盖另一项目或新输入。

## Python 接口

桌面控制台使用 `stk.project.drafts`；直接使用本地存储时是 `ProjectStore(directory).drafts`，
方法签名及返回值相同。调用者提供规范的小写带连字符 UUID，并保留它用于查询和不确定响应恢复：

```python
from uuid import uuid4

p = stk.project
base = p.snapshot()["project"]["revision"]
draft_id = str(uuid4())
commands = [{"op": "create_table", "name": "拟议参数表"}]
draft = p.drafts.save(
    commands,
    expected_revision=base,
    title="准备温度参数表",
    draft_id=draft_id,
)
print(draft["commands"])  # 已分配新对象 UUID；表格尚未修改
print(p.drafts.list(offset=0, limit=100))
print(p.drafts.get(draft_id))
```

保存内部调用预览引擎，校验普通命令和基础修订后记录实际命令。对象 ID 未提供时只分配一次；
草案 ID 必须由调用者明确提供。名称为最多 1024 字符的非空白字符串；命令为 1–1000 条，
规范 JSON 的 UTF-8 大小最多 256 KiB，生成 ID 后也检查此上限。预览仍受源数据库逻辑大小 128 MiB 限制。
命令格式或对象错误拒绝保存；候选公式错误遵循普通编辑规则，不能把成功保存理解为全部计算有效。

在另一次明确决定中应用，或放弃：

```python
# 应用前在原生检查页载入并核对，或在脚本中检查同一批命令的 preview 结果。
receipt = p.drafts.apply(draft_id, expected_revision=draft["base_revision"])
print(receipt["draft"]["status"], receipt["revision"], receipt["replayed"])

# 另一份仍待处理的草案可以明确放弃：
# p.drafts.discard(other_draft_id)
```

Python `apply` 是显式修改入口，不等待原生按钮或把保存当作审批；它只使用已保存的命令，
不接受替换命令。`expected_revision` 必须等于原草案基础修订，待处理草案还须匹配当前项目修订。
旧草案不能通过提高此参数强行应用，应核对当前数据并保存新的草案。

| 方法 | 返回值 |
|---|---|
| `save(commands, *, expected_revision, title, draft_id)` | 完整草案 |
| `get(draft_id)` | 完整草案及当前保存状态 |
| `list(*, offset=0, limit=100)` | `{drafts: [不含 commands 的摘要], next_offset: 整数或 null}` |
| `apply(draft_id, *, expected_revision)` | `{draft, revision, replayed}` |
| `discard(draft_id)` | 标记后的完整草案 |

列表按保存顺序分页，包括终态记录；`limit` 为 1–100，`offset` 为非负整数。
当前没有删除记录、覆盖已保存命令或草案 CLI 子命令。

## 状态与响应恢复

完整草案只有以下公开字段：

| 字段 | 含义 |
|---|---|
| `id`、`project_id` | 草案与所属项目的稳定 UUID |
| `title`、`created_at` | 保存名称与创建时间 |
| `base_revision`、`commands` | 冻结的基础修订与普通编辑命令 |
| `status` | `pending`、`applied` 或 `discarded` |
| `applied_revision` | 应用成功的修订，否则为 `null` |
| `closed_at` | 应用/放弃时间，待处理时为 `null` |

“过期”是基础修订与当前修订的比较，不是第四种保存状态。草案不保存完整项目快照、预览差异、
聊天消息、模型输出或审批人；本轮的回执只说明这份命令是否已应用或被放弃。

- **保存响应不确定**：先通过保留的 UUID 查询。也可用同一 UUID、相同原始命令、名称及基础修订
  再次调用 `save`，返回原记录，包括原来生成的对象 UUID；即使项目已继续修改也不另存一份。
  同一 UUID 配不同请求返回 `conflict`。接口不自动重试；不要在不确定时重新生成草案 ID。
- **应用响应不确定**：查询原草案，或用原 UUID 和原基础修订再次明确调用 `apply`。
  已应用时返回 `replayed=true` 和原应用修订，不再次修改数据。该修订可能早于项目当前修订。
  即使原编辑后来已被撤销，回执仍为已应用，重试不会重做；需要重做时使用普通项目重做，或另建新草案。
- **放弃**：重复放弃返回原终态；已应用草案不能放弃，已放弃草案不能应用。没有重置为待处理的入口。

保存/放弃与普通撤销历史分离，不提升编辑修订、不发布 `project.changed`。首次应用只增加一次修订，
按普通编辑进入历史和撤销栈，并发布该事件；回执重放不发布。保存记录位于项目 SQLite 的 `project_drafts`，
数据库备份包含它们，但不是包含外部资源的完整项目备份。

格式 7 可将草案与同一基础修订的上下文、文字消息关联，见[上下文指南](project-contexts.md)及
[设计边界](design/review-drafts-and-conversations.md)。来源关联不会改变草案状态或代替明确应用；模型集成仍待开发。
